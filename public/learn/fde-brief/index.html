如何使用

《智能体工作流设计：方法与实践》配套扩展指南。示例为虚构教学场景，不是实际客户案例、招聘标准或原书新增章节。

你不需要第一天就写完架构、评测和上线方案。先找到一个具体的人、一件重复的事，做出能让对方试用的小成果，再把缺口补齐。

怎么使用这份任务书

  • 第一次做：先填“起步六问”，不确定的写“待确认＋找谁确认”。
  • 已有演示：补“试用与验证”，检查真实问题能否解决。
  • 准备上线：再补“上线与交接”，与客户和技术负责人共同确认。
  • 你负责业务、实施或客户沟通：可以先完成访谈、流程、样例和验收设计；代码接入与生产权限请和工程同伴分工。
  • 你负责开发：不要跳过访谈。先确认谁使用、怎样算有用，再选择工具。

这是项目协作底稿，不是考试。空缺是下一次沟通的议题，不意味着你“不够专业”。

一、起步六问：先把这张卡填好

1. 谁遇到了什么问题？

填写：我想帮助【哪类使用者】，在【哪个场景】完成【具体任务】，目前最麻烦的是【什么】。

示例：帮助新同事查找差旅报销要求。目前他们要翻多个文档，遇到不确定的条款仍需询问行政。

  • 最近一次发生这个问题的经过：

2. 现在是怎么做的？

填写：从接到任务到完成，列出三至五步。圈出等待、重复输入或容易出错的地方。

示例：员工提问 → 搜索制度文件 → 判断适用条款 → 找行政确认 → 整理回复。

我的版本：

  • 当前步骤：
  • 最想改善的一步：
  • 现有证据：一条脱敏问题、一份获准使用的材料或一次观察记录。

暂时没有耗时数据，就写“待测量”；不要先编一个节省比例。

3. 这次只做什么？

填写：这一轮只覆盖【一个流程片段】，交付【一种可检查的成果】。

示例：先用一份模拟差旅制度，做一个“回答＋原文出处＋不确定时转人工”的问答演示。

我的版本：

  • 本轮范围：
  • 可展示的成果：
  • 暂不做：

示例中的“不做”：不接真实员工信息、不自动审批报销、不替代行政解释、不承诺支持所有制度。

4. 输入从哪里来，结果给谁看？

填写：输入【资料/问题】，来源【出处】，输出【格式】，由【谁】确认。

示例：输入为自编的两页制度和五个模拟问题；输出为简短回答、引用段落和待确认事项；同伴扮演行政审核。

我的版本：

  • 资料来源与版本：
  • 是否获准用于本项目；谁可访问：
  • 输出格式与接收者：
  • 人工确认人：

没有资料授权时，用公开且允许使用的材料或自编素材练习，不先上传客户内部文件。

5. 怎么知道“做对了”？

先准备几个小样例。下面是教学起点，不是生产验收标准。

  • 正常问题：材料里有答案，应给出对应出处。
  • 未知问题：材料未说明，应明确说不知道并指向人工确认。
  • 含糊问题：缺少关键信息，应先追问。
  • 权限问题：如果项目涉及不同角色，不能让无权用户看到受限内容。
  • 资料变化：更新材料后，应确认回答仍指向正确版本。

我的版本：

  • 样例问题：
  • 期望结果及判断依据：
  • 实际结果与差异：
  • 谁检查，什么时候检查：

6. 下一步做什么？

填写：由【谁】在【约定时间】完成【一个动作】，带回【证据/成果】，再决定是否继续。

示例：本周先请一位同伴用五个模拟问题试用，记录卡住的位置与错误回答，修订后复测。

  • 下一步动作与负责人：
  • 需要谁协助：

二、一个完整的起步示例

项目名称：新同事差旅制度问答（模拟练习）。

使用者：新入职员工；需求确认人：同伴扮演行政。

当前流程：找文件、定位条款、询问行政、整理回复。

这一轮：只处理一份自编制度的问答，输出答案与引用；找不到依据就转人工。先在本机演示，不对外上线。

实现选择：先做人工检索与回复模板，作为对照；再按需要选择现有工作流工具或代码。若人工模板已经够用，不为了“智能体”增加复杂度。

验收方式：用事先写好的问题与期望答案逐条检查，记录错误、不确定项和修订。问题数量按风险与实际覆盖需求扩展，不把小样例通过当成可以生产上线。

第一次试用要问：你是否找到了想要的信息？出处是否方便核对？哪句话不清楚？你下一次还会在哪一步需要人工帮助？

暂不覆盖：审批、金额计算、跨部门权限、真实身份认证、多份冲突制度。

下一步决策：如果主要障碍是资料混乱，先整理资料；如果是答案难核查，先改善引用；只有确认试用价值后，再讨论系统接入。

三、跟客户聊什么：先聊任务，再确认责任与费用

  1. 能带我看一次最近完成这件事的过程吗？
  2. 哪一步最容易卡住？卡住后通常找谁？
  3. 如果这次只能改善一件事，你最希望是哪件？
  4. 你会用什么例子判断这个结果能不能用？
  5. 正常完成这件事时，谁发起、谁操作、谁审核、谁决定结果可以使用？
  6. 哪些事必须由人确认，哪些资料不能用于试验？
  7. 客户、FDE和平台供应商分别负责什么？上线后谁每天维护，负责人不在时谁代班？
  8. 账号、云资源、模型服务和数据由谁提供、管理和付费？项目结束后归谁？
  9. 这轮可投入多少人力和费用？哪些包含在约定范围内，新增需求或超预算由谁批准？

记录对方原话、观察与自己的推测，分开写。客户说“做个万能助手”时，先一起选一个高频任务，不急着承诺全覆盖。

四、试用与验证：有演示后再补

  • 现状对照：当前人工方法怎样完成同一任务？
  • 样本与口径：哪些任务可以比较，哪些不可以？
  • 结果记录：是否正确、是否有依据、是否需返工、人工检查用了多久？
  • 失败记录：输入是什么、哪里失败、影响谁、怎样人工处理？
  • 使用反馈：用户在哪一步放弃、哪里难理解、还缺什么资料？
  • 继续条件：客户认可哪些结果？还要补哪些证据才能扩大范围？

复盘句式：我们观察到【现象】，证据是【记录】；可能原因是【推测】，下一次通过【动作】验证。

五、上线与交接：准备接真实业务时共同填写

先把日常工作由谁负责说清楚，再讨论异常。以下为项目协作模板，由客户、FDE及相关负责人共同确认；不因填写本表自动替代双方已有约定。

1. 正常业务：每一步都有执行人和确认人

不只在故障时找人。即使系统正常运行，也要明确结果由谁使用、审核和承担业务决策责任。

按“事项｜执行人｜最终确认人｜协作人｜完成证据与时限｜替补人”逐项填写；可以一人兼任，但不要只写“客户负责”或“技术负责”。

  • 需求与范围：谁提出任务、确认优先级、接受范围变更。
  • 资料与规则：谁维护内容、确认准确性与允许用途，规则变化后谁通知项目组。
  • 日常执行：谁发起任务、检查输入、查看结果、处理待办；自动执行的任务由谁监督。
  • 输出使用：谁审核、批准发送或业务执行；允许自动放行的范围、规则和批准人是什么。
  • 技术运行：谁维护工作流、模型和接口配置，谁发布版本、复测变更。
  • 验收与结项：谁确认交付达到约定标准，谁接收材料并确认后续维护安排。
  • 持续运营：谁处理用户问题、安排回访、维护知识和记录使用效果。

模拟示例：报销制度问答中，行政维护制度并确认解释口径；FDE负责约定范围内的流程实现和测试；员工确认问题背景，正式报销仍由原业务审批人决定。问答回答不自动等于审批通过。客户技术管理员负责其接收的部署环境。真实项目应把这些角色替换为双方确认的具体人员。

我的责任清单：

  • 事项 / 执行人 / 最终确认人：
  • 协作与替补人员：
  • 完成证据、处理时限与沟通渠道：
  • 尚有分歧的责任及确认时间：

2. 账号与资源：不只是保管一把密钥

覆盖客户账号、服务账号、API密钥、模型额度、云主机、数据库、代码仓库、域名及第三方订阅。逐项记录归属、管理员、允许用途、费用承担者和到期时间。

  • 谁申请、批准和创建资源，谁可以授权、调整权限与撤销访问。
  • 谁保管凭据，存在哪里，谁执行轮换、到期续订与离职回收；不要把实际密码或密钥写进任务书。
  • 开发、测试与生产是否分开；FDE临时访问何时到期，客户何时接管。
  • 谁维护资源配置、备份与恢复，谁查看访问记录和费用账单。
  • 项目结束后账号、代码、配置、数据和剩余额度怎样交接；哪些应保留、导出、删除或停订，由谁确认完成。
  • 第三方服务变更、不可用或停服时，谁协调供应商并决定替代方案。

我的资源清单：资源名称 / 所属方 / 管理人 / 授权范围 / 付费方 / 到期日 / 交接动作。

3. 成本与费用：先说清总账，再谈节省

原来的“运行预算”只是其中一项。至少分开记录一次性交付成本、持续运行成本与后续变更成本。

  • 一次性交付：需求访谈、资料整理、开发集成、测试、部署、培训与交接的人力；差旅、现场支持与采购费用按实际情况列出。
  • 持续运行：模型调用、工作流平台、云资源、存储与流量、外部API、软件订阅；人工审核、日常运维与客户支持也要计入。
  • 后续变更：新增场景、接口调整、知识更新、模型迁移和返工；区分原范围内修正与新增需求，约定判断和批准方式。

每项填写：费用名称 / 估算依据与使用量 / 单价来源与日期 / 一次性或周期性 / 预计费用区间 / 付费方 / 批准人。未知费用写“待询价”，免费额度到期后的费用也需确认。

计算起点：某周期总成本＝该周期分摊的一次性交付成本＋资源与调用费用＋人工审核及运维费用＋已批准的变更费用。估算时说明周期、用量、重试次数和假设；不要把一个演示的低费用直接当成生产成本。

商业沟通需要确认：

  • 哪些工作和费用包含在报价或项目范围内，哪些由客户另行采购。
  • 谁先支付、是否允许代垫、按什么凭证及节点结算；未经约定不要默认FDE个人垫资。
  • 预算上限、提醒阈值、账单查看人和复查频率；触及上限后是限流、暂停还是申请追加，由谁决定。
  • 新增需求先记录影响、费用与交期，由指定人员批准后再执行。
  • 试用、上线和维护分别覆盖多久，续费、退出和资源停订由谁处理。

模拟填写方式：本轮只做本机演示，不采购付费资源；如需接入付费模型，先由指定负责人确认费用估算与付款账号，再启用。这里不预设客户一定同意，也不虚构预算金额。

衡量价值时，对比同类任务原有人工成本、返工和新方案的完整成本；没有基线或可比样本，就先记录成本与测量计划，不承诺收益比例。

4. 异常与交接：提前约定怎样接手

  • 人工接管：谁接手、触发条件、响应时限、升级联系人与用户提示。
  • 停止与回滚：谁可以停用、怎样恢复原来的可用办法、谁验证恢复结果。
  • 交接材料：启动步骤、已知限制、测试记录、日常责任清单、资源清单、费用清单和维护联系人。
  • 交接确认：接收方是否能独立操作、是否拥有所需权限；未完成事项由谁在何时补齐。
  • 试运行复查：何时回访使用者，谁收集反馈，怎样决定下一轮范围与预算。

练习可以先演练；接入真实业务前，由相应负责人确认日常分工、资源授权和费用安排。FDE负责推动缺口得到确认，不默认替客户承担所有业务决策、资源支出或长期维护。

六、和本书怎么一起用

  • 第1—3章：理解业务流程、工作流与智能体工作流，帮助回答起步六问。
  • 第4—6章：结合设计模式与构建方法论，说明为什么这样设计、怎样检查。
  • 第7—10章：结合平台、编排与自动化主题，选择实现方式。
  • 第11—13章：从教育、营销、制造场景寻找可缩小为练习的任务。

以上是平台建议的使用路线，不代表书中包含本任务书或某项认证要求。

七、交出去之前看一眼

  • □ 一句话能说清帮助谁、解决什么问题。
  • □ 有一个具体输入和可检查输出。
  • □ 已写明资料来源、人工确认人与暂不做事项。
  • □ 至少记录了一次试用或明确的试用计划。
  • □ 未确认的信息没有包装成成果。
  • □ 日常执行、结果审批、验收和维护都有明确负责人。
  • □ 账号与资源归属、授权、付费和退出安排已确认或列为待办。
  • □ 交付、运行、人工审核与变更成本均已估算或标明待确认，付款与预算批准人明确。
  • □ 下一步动作有负责人。
